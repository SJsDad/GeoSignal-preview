# TT04PWM Render 실행 가능성 검토

## 결론

**현재 앱에서 바로 사용할 수 있는 것은 기존 Speed 옵션이다. 새 후보는 계산 자원상 실행 가능한 범위가 있지만 제품 연결이 필요하다. Free에서는 프리뷰를 먼저 연결하고, 보통은 단일 초점·소수 ROI의 opt-in으로, 정밀은 캐시 또는 소수 ROI로 제한하는 것이 타당하다. 보통/정밀의 전체 Focus/Dose Sweep은 현재 300초 동기 요청에 적합하지 않다.**

이번 검토는 배포가 아니다. `app.py`, `src/service.py`, Production 광학·Raster·Gauge, `render.yaml` 및 기본값을 변경하지 않았다. 수치 벤치마크를 실제 TT04 Polygon에 적용하고, Linux HTTP 검증 스크립트의 오래된 검사 항목을 수정했다.

## 확인한 환경과 Layer

- 검토 기준 checkout: `work`, `eb252a6363c881cb1f69a1652af633d7c58462ad`.
- `render.yaml`: **Free, Python3.11.9, Gunicorn 1 worker, timeout300s**, pya-native. 인증된 Render Dashboard의 현재 설정·배포 SHA는 조회하지 않았다.
- [Render 공식 Compute Plans](https://render.com/docs/compute-plans): Free 0.1CPU/512MB, Starter(`0.5c-512mb`) 0.5CPU/512MB, Standard(`1c-2g`) 1CPU/2GB. 이번 실험은 Free 동급 **Docker 0.1CPU·512MiB·swap 없음**이다. 실제 Render 하드웨어나 부하를 재현한 것은 아니다.
- 실행 Cloud: 2CPU quota/8GiB. Python 및 패키지 버전은 `environment.json`에 저장했다. Docker는 기존 Debian12 이미지를 사용하고 동일 Python/venv/코드를 읽기 전용 mount했다. 컨테이너 네트워크는 사용하지 않았다.
- GDS: `data/tinytapeout/tt04_pwm.gds`, SHA256 `464528a971396cdec3a9ae4da1c800092f3e3035ae72f242c539a1601321cada`. **67/20와 68/20 모두 존재한다.**
- 67/20: 제품에 등록된 중심(147.770,108.460)µm, y축, 설계170nm gauge 사용.
- 68/20: 제품에 등록된 기준이 없다. 실제 Width 후보의 중심(129.490,91.3125)µm, x축, 설계140nm를 선택하고 제품과 같은 Polygon transect 검사로 확인했다. 이는 새로 등록·검증된 제품 Calibration 기준이라는 뜻이 아니다. 현재 앱에서는 이와 같은 유효한 Custom Anchor 입력이 필요하다.
- 두 Layer 모두 innerROI2.56µm + ambit0.32µm = **FFT domain3.20µm**를 유지했다. KrF λ248nm/NA0.68/σ0.60, rawT0.30/D0=1.0이다. 아래 어댑터 비교는 dose fitting을 하지 않았다.

## 4개 후보의 실측 자원 비용

아래 시간은 **Free 동급 quota에서 실제 실행한 1ROI 준비+nominal Abbe+선택 보간 Gauge**이다. GDS read/clip/Area 변환/Mask FFT/Source/field 준비를 포함하고, Python import·DRC 후보 추출·dose calibration·Contour/그림·CSV/GDS/HTML 출력·네트워크는 제외한다. 따라서 서비스 전체 TAT가 아니다. 각 Layer의 Shape/Source/Area/Gauge 검증이 통과했다.

|기존|Equal Dense7 / 29|10 / 10|Binary / Bilinear|2.125|1.427|67 바로 가능, 68 Anchor 필요|단일 초점 기존 경로 유지|
|빠른 프리뷰|Equal Dense7 / 29|25 / 25|Exact Area / B-Spline|3.000|2.021|미연결|연결 후 가능. 최초 준비는 기존보다 느릴 수 있음|
|보통|Cell-area Dense51 / 2077|10 / 25|Exact Area / B-Spline|19.118|18.191|미연결|단일 초점·소수 ROI부터 조건부 가능|

Quota run은 8조건을 한 프로세스에서 순차 실행하여 Source를 재사용했다. Source 생성은 처음 만난 설정에서만 발생하며 stage JSON에 cache hit의 실제 시간이 남아 있다. Mask/FFT는 각 case에서 새로 계산했다. 각 quota 시간은 1회 실측으로, 100ms CPU quota period의 burst/대기 위치에 따라 짧은 stage의 wall time은 크게 변할 수 있다. Native는 조건별 독립 프로세스, 광학 계산 median3이다. 이를 더 큰 유효숫자의 성능 순위로 해석하지 않는다.

**Raster와 광학 비용을 나누면 결론이 명확하다.**

|옵션|67/20 Raster, quota s|67/20 nominal광학, quota s|67/20 nominal광학, Native median3 s|68/20 nominal광학, Native median3 s|
|---|---:|---:|---:|---:|
|기존|0.009|0.802|0.0739|0.0715|
|프리뷰|2.398|0.101|0.0082|0.0094|
|보통|10.909|6.595|0.6008|0.5906|
|정밀|43.603|6.405|0.6133|0.8114|

프리뷰는 준비된 Mask/FFT가 있으면 광학 계산이 기존보다 약8–9배 빠르다. 그러나 현재 일반 Polygon Exact Area 구현은 모든 pixel을 순회해 최초 준비가 비싸다. 따라서 앞선 이상적인 periodic L/S의 0.009초를 실제 TT04 서비스 전체 시간으로 사용할 수 없다. 보통과 정밀은 Source와 AI Grid가 같아 반복 광학 비용이 비슷하며, 주요 차이는 Mask 준비다. 큰 Source의 명목 광학 계산은 기존 대비 약8–11배 비싸다.

메모리는 Native 독립 worker peakRSS **123–146MiB**, quota 공유 프로세스 누적 peakRSS **145.1MiB**였다. 5nm Mask640²도 streaming Abbe+AI128²에서는 이 범위 안에서 실행됐다. 현재 5nm 불가는 먼저 소프트웨어의 `max_pixels_per_axis=384` 제한 때문이며, 이 결과를 근거로 메모리 부족이라고 단정하지 않는다. 새 옵션의 전체 HTTP peak는 미측정이다. 모든 Source의 coherent field를 저장하거나 큰 전체 Layout을 한 번에 Rasterize하면 이 메모리 결과가 적용되지 않는다.

## 기존 제품 전체 HTTP 요청 검증

**Free 동급 전체 HTTP smoke PASS.** 실제 Gunicorn1worker/timeout300s에서 TT04 67/20 Speed 업로드→결과 HTML 요청이 **119.899초**, cgroup 전체 peak memory **350.16MiB**로 완료됐다. 응답 4,395,833bytes, reference nominalCD **170.018074nm**, D0 **0.82421875**. Peak는 같은 컨테이너의 master/worker/client와 charged page cache를 포함하며 per-worker RSS와 다르다. 이는 컨테이너 실측이며 현재 Render에 업로드한 결과는 아니다. 기본 Focus/Dose Sweep은 꺼진 요청이다.

기본 `process_window`는 **꺼져 있다**. 현재 Speed 요청은 후보 최대5개와 별도 reference를 준비하고, 설계 CD로 D0를 맞춘 뒤 preview/다운로드 파일을 만든다. 선별된 단일 ROI 어댑터 시간과 이 전체 요청의 시간은 별개다.

초기 HTTP smoke는 보이는 HTML에 내부 ID `REFERENCE_ANCHOR`가 있어야 한다고 검사해 false failure를 냈다. 실제 화면과 CSV는 정상임을 Native 응답을 디코딩해 확인했다. 검증을 reference CSV 존재·nominal VALID·170nm±0.1nm·양의 D0로 고치고 응답 HTML을 성공/실패 모두 저장하게 했다. Production 동작 변경은 아니다. 초기 assertion 실패를 Render 계산 실패로 해석하지 않는다.

과거 실제 공개 Render의 Speed 요청109.28초 관측 기록은 `docs/v010_release_validation.md`에 있다. 당시 서버 peak memory와 실제 배포 SHA는 확인되지 않았다. 이번 컨테이너 시간을 현재 호스팅 실측으로 표기하지 않는다.

## Focus/Dose Sweep과 300초 제한

전체 Sweep을 켜면 기본값은 **17focus × 21dose**이다. 21dose마다 FFT를 다시 하는 구조가 아니다. 각 ROI에서 17개 focus 이미지를 계산하고 dose는 threshold를 바꿔 계측한다. 다중 ROI의 Source별 IFFT가 주요 추가 비용이다.

Native에서 0/−0.2/+0.2µm 초점을 실제 측정했다. 6ROI×17focus의 광학 계산만 CPU시간/0.1CPU로 환산하면 기존 **145–160초**, 프리뷰 **18–19초**, 보통 **1320–1819초**, 정밀 **1322–1674초** 수준이다. 이는 −0.2/+0.2의 비용을 나머지16개 focus에 적용한 **규모 추정**이며 전체17focus·실제6ROI·HTTP 실측이 아니다. Raster/계측/출력 비용도 제외했다. 실측과 구분하여 `focus_cost_estimate.csv`에 저장했다.

이 추정에서도 보통/정밀은 Free의 300초 동기 요청에 부적합하다. 단순히 timeout을 늘리는 대신 ROI/focus 수를 제한하거나 background job으로 분리해야 한다. 0.5CPU에서는 이 광학 추정이 약264–364초이므로 전체 Sweep의 충분한 여유가 확보되지 않는다. 전체 Sweep까지 제품 지원하려면 1CPU/2GB급에서 실제 E2E 검증을 권한다. 플랜 변경·배포는 수행하지 않았다.

정밀의 최초 1ROI 준비 포함49–51초를 6개 비슷한 ROI에 적용하면 **약295–307초**로, 출력·보정 비용 전부터 300초에 근접한다. 이 역시 대표 ROI에 대한 규모 추정이며 실제 기본6ROI 수행값이 아니다. 정밀을 Free의 기본 옵션으로 권하지 않는 이유다.

## 제품 연결에 필요한 변경과 적용 순서

1. **Exact Area + B-Spline opt-in부터 연결.** Pixel을25nm로 바꿔도 현재 API는 Binary/Bilinear를 사용하므로 신규 프리뷰가 되는 것은 아니다. 일반 Polygon Area는 경계 cell에 계산을 집중하는 최적화와 Mask/FFT cache가 우선이다. B-Spline은 Gauge와 Contour 모두 raw intensity에서 일관되게 적용하고 boundary 조건을 검증해야 한다.
2. **보통: Cell-area51 + Mask10/AI25.** Source 생성/가중치, service의 Source 선택과 ProcessWindow 허용 모드, fine Mask→coarse field FFT와 물리 좌표 metadata를 연결한다. 처음에는 nominal focus, 소수 ROI로 제공하고 실제 전체 요청을 재검증한다. 주어진 quota에서 1ROI 계산은 완료됐지만 새 조합의 D0 calibration/Contour/HTML 전체 성공은 아직 보증하지 않는다.
3. **정밀: Mask5/AI25.** 독립 Mask cap640 이상과 AI cap을 분리하고 request memory budget을 둔다. ROI2.56/ambit0.32를 조용히 줄여 같은 실험처럼 비교하면 안 된다. 캐시 없는 다중 ROI는 Free 기본값으로 두지 않는다.
4. **68/20 기준 등록은 별도 검증.** 이번140nm gauge는 실제 Geometry에는 맞지만 범용 optical reference 수렴과 모든 focus/dose의 CD 안정성을 검증한 것은 아니다. 67/20의170nm gauge를 그대로 재사용하지 않는다.

이전 L/S+Contact의 최대 CD오차(프리뷰15.394nm, 보통1.342nm, 정밀0.440nm)를 이 TT04의 오차 보증으로 옮기지 않는다. 이번 TT04에는 연속 Source/정밀 Geometry에 대한 독립 optical accuracy reference를 만들지 않았으므로 출력 CD는 오차가 아니다. Equal/Cell-area는 균일 원형 Source의 quadrature이며 실측 장비의 Source 분포가 아니다.

## 재현·완료 범위

실행한 범위: 2Layer×4후보 Native 8조건, 동일한 Free 동급 quota8조건. Native focus0/−0.2/+0.2와 nominal/defocus 광학 median3, quota nominal1회. 물리 Geometry transect, Source count, fixed domain/shape, Exact Area 보존(<1e−10µm²), Native/quota CD 일치(<1e−9nm)를 확인했다. 관련 수치 회귀 **40개 통과(2.00초)**. 기존 전체192개 회귀 통과 기록은 앞선 Snapshot이며 이번에는40개를 재실행했다.

미실행: 새 세 후보의 실제 Render 배포·전체HTTP, 새 후보의 전체 default6ROI와17focus sweep, TT04 연속 Source 기준 CD accuracy/EPE, cache 기반 전체 요청 및 동시 사용자 부하. 실제 Render Dashboard CPU/RAM 로그·배포 SHA도 미조회다.

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 .venv/bin/python -m experiments.benchmark_render_feasibility --output work/render_feasibility/native
```

컨테이너 안에서는 `--mode quota --output work/render_feasibility/quota`로 실행한다. Docker는 `--cpus 0.1 --memory 512m --memory-swap 512m`, Python3.11.9와 같은 의존성을 사용해야 한다. 정확한 bind mount 명령은 `REPRODUCE.md`에 있다. case JSON은 설정/실험 코드 fingerprint가 일치하면 완료 case를 재사용한다. GDS hash도 확인한다. Production dependency 변경 시에는 출력 디렉터리를 분리해야 한다.

산출물: 실행 CLI/JSON 설정, `TT04_RENDER_FEASIBILITY.csv` 실측16행, 모든 stage와 반복 시간 `RUNTIME_DETAILS.json`, CPU 환산 추정 CSV, 환경 JSON, 한국어 본문 및 전체HTTP 실측 JSON. 오래된 외부 HTTP assertion 실패는 이 보고서에 명시했다.
